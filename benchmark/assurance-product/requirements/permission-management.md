# 角色权限模块测试需求

测试 vue-fastapi-admin 的角色管理、菜单/API 授权与访问控制，仅覆盖 API 层，执行完整 full workflow。

## 范围

- `GET /api/v1/role/list`、`GET /api/v1/role/get`：分页、角色名称筛选、角色详情。
- `POST /api/v1/role/create`、`POST /api/v1/role/update`、`DELETE /api/v1/role/delete`。
- `GET /api/v1/role/authorized`、`POST /api/v1/role/authorized`：读取、授予、替换和清空菜单/API 权限。
- 通过本轮创建的用户绑定测试角色，验证授权前、授权后、撤权后的真实受保护接口访问结果。
- 登录、用户绑定角色、菜单和 API 目录接口仅作为本 item 的身份与授权依赖；不扩展成用户、菜单或 API 目录的完整 CRUD benchmark，不执行全局 API refresh。

## Benchmark 非交互确认

以下范围由 benchmark owner 确认，作为本 item 的验收输入：

- 角色 CRUD 的正常流程；角色名称必填、非空、长度和唯一性遵循 `.aa/data-knowledge.yaml` 的 `entities.role` 及已验证源码约束，不自行发明长度阈值。
- 授权读回的菜单/API 集合应与提交的有效授权一致；重复授权不能形成重复关系，替换和清空权限不能保留已撤销的权限。
- 普通用户只能访问其角色获准的受保护 API，权限匹配使用已验证的请求 method 和 path；未授予和撤销的权限必须拒绝，不能通过错误方法或类似路径获得权限。
- 以请求本身可成功处理的合法参数验证授权边界，避免被无关参数错误、资源不存在或登录失败抢先拦截。
- 未登录、无角色普通用户、空权限角色用户、具备对应权限的普通用户，以及超级管理员分别验证适用的权限边界。超级管理员按受测接口已发布的组织约束评估，不把源码绕过授权的现状自动当作正确，也不自行增设未授权的权限政策。
- 菜单授权通过角色授权读回及现有当前用户菜单接口（如源码存在）核对，前端展示不属于本轮范围。
- 无效角色、菜单或 API 标识不得产生悬空授权关系；被拒绝的授权变更不得破坏原来的有效授权。删除本轮测试角色后不得留下可继续生效的授权关系。
- 已确认需求与源码不一致时保留期望和证据，交由后续执行、Inspect 和 Report 记录真实结果，不为得到绿色结果修改 SUT。

## 数据与证据边界

- 使用新的 change ID、独立 SUT 副本和独立数据库，保留之前部门、用户 item 的全部产物和执行证据。
- 所有写操作只针对本轮创建的角色、用户、菜单和关联。不得修改或删除初始化管理员、系统角色、现有 API 注册目录及 benchmark driver 的运行身份。
- 授权测试读取现有 API 目录以选择真实受保护路由，只为本轮测试角色建立或删除授权关系。
- 测试数据使用本轮唯一前缀、合法邮箱，并规划逆序清理用户、角色和菜单及其关联。清理不得波及已有业务数据。
- 管理员身份来源必须有初始化源码事实依据；init 不写用户名或密码，不假设 `admin / admin`，不引入 opaque-token 新方案。
- 沿用既有模型、路由和 rounds/retry 预算；不在本轮手工修正 review 输出、冻结计划、生成测试或部署中的 wheel。
- 不自动提交代码、MR 或外部缺陷单；Retro 不包含在本轮 full 入口中。
